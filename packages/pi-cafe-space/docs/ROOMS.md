# 房间链接与二维码

## Café账号登录与访客

Space首次进入可以选择「使用 Café 账号登录」或「以访客身份继续」。Café账号复用cafecode.work原登录和二次验证，不需要再注册Space账号；主站有登录时无需重复输入账号密码。账号显示主站昵称#固定ID，访客可以自定义昵称。

从房间链接或二维码进入时，登录成功或取消都返回原房间。账号登录只证明身份，两类访客都要输入房间密码；账号密码只在主站输入，Space只询问房间密码。审批关闭时两类访客均可直接操作；开启时都要房主批准，主站管理员不自动成为房主。

同账号跨设备有相同显示ID，但不会自动共享Pi控制权；切换账号或改成访客也不继承旧批准。身份菜单提供仅退出Space与确认退出所有Café应用，不取消已经运行的Pi任务。账户过期或主站停用后需要重新登录，不能静默降级为访客。访客入口不依赖主站在线。

当前账号入口已在公共Space和本机网关接通，刷新网页即可，不需要为此/reload Pi。新的办公网关需要显式配置与公共来源匹配的accountIssuer；未配置的自托管实例不自动信任其他身份提供方。详细有效期与部署记录见[CAFE_SSO.md](CAFE_SSO.md)。

## Pi内审批与模型配置

在空闲时执行`/reload`加载最新扩展。房间启用审批后，新访客申请操作当前Pi时会出现一条简短提示，使用`/cafe approvals`或`/cafe`主菜单的审批项查看。选择具体申请，再选择批准或拒绝，并确认才提交；不自动批准或发送草稿。只展示当前Pi的申请，网页批准与撤销继续有效。此功能只用于房主本机交互式Pi，依赖私有本机房主凭据；只有Pi host令牌不能审批，RPC模式不开放。

模型思考等级始终以原生Pi实际值为准。`reasoning:false`会令Pi只接受off，不应通过更换select误判为已解决。修改本机models.json后，可在空闲Pi执行`/cafe models`重新读取本机配置并刷新同一模型能力，不重启会话或更改默认等级。然后在网页模型面板选择支持的等级；被Pi钳制或不支持会显示明确错误。该设置是否影响上游模型仍依赖provider的实际参数支持，本地状态接受不构成上游验证。

## 用户流程

终端扫码困难时，推荐在分享面板按 **P**，或直接输入 **`/cafe qr`**：浏览器会打开本机生成的高清SVG二维码预览，无需登录，编码的仍是同一房间链接，不含密码。页面没有脚本或外部资源；只在用户主动操作时生成，临时文件为用户私有，15分钟或扩展停止时清理。

macOS Terminal 的块字符会受字体行距影响，因此默认改用完整背景格绘制实心码，不再默认显示横线断裂的半块码。按Q看终端码，S切换实心/紧凑；空间不足会提示所需列数/行数而不裁剪。在96×36这类窗口里直接按P比调整字体更可靠。其他终端保留改进的紧凑模式；字形比例仍由终端决定，实心或SVG是可靠退路。

一台办公电脑的 Café Space 网关对应一个房间，房间里包含该网关 `main` 范围内的多个 Pi 实例和原生会话。不是给每个 Pi 分配独立房间，也不要求访客注册云端账户。

**推荐从Pi直接开始：输入 `/cafe`，选择默认的“分享房间”，或直接 `/cafe share`。** 终端展示二维码与完整链接，C复制、B网页管理、R刷新、Esc返回；启动不会自动弹浏览器。状态分开说明本Pi是否加入、房间是否在线及共享实例数量。终端空间不足或SSH剪贴板不可用时给出明确备用方法，不虚报成功。

网页仍可使用：`/cafe open`打开本机分享直达页，需要登录时按原本机令牌登录后自动回分享。手动打开工作台（默认 `http://127.0.0.1:37891/`）也可点击顶部“分享房间”。现在只需一个入口：「分享房间」面板顶部有「分享 / 房间设置」两页。分享页突出二维码和复制链接；房间设置页集中管理控制权审批、密码及链接重置。直接打开本机根路径也能找到设置，窄屏本机页面顶部有分享图标。点击“复制链接”可分享给笔记本；手机使用系统相机扫码，选择身份后进入房间密码页。二维码在浏览器本地生成，不调用第三方二维码服务，不包含密码、内部 host 密钥或房主私钥。

分享地址格式为 `https://space.cafecode.work/#/room/<roomKey>`。公共首页只提供粘贴链接/key的入口，不列出其他人的电脑、房间或会话。访客打开链接后输入6–20位房间密码，密码验证成功才出现实例、会话和控制界面。关闭网页不停止 Pi。

首次从当前已初始化本机版本迁移时，房间密码沿用已有本机登录令牌；之后两者独立。“分享房间 → 房间设置 → 修改房间密码”只改访客密码，不改本机登录令牌或链接。“重置房间链接”需要确认，更新房间key和二维码、保持房间密码不变。两种变更都会断开当前访客以重新授权，不终止 Pi 任务。

办公电脑或网关重启、Pi实例增减不改变链接。离线或无效房间显示不可用；不要为展示初始化页删除凭据。房间身份文件丢失无法凭公开链接恢复私钥，应当从私有备份恢复或明确生成新链接。

## 多人访问与权限

同一链接和密码可供手机、笔记本与协作者分别连接办公网关。**控制权功能默认关闭：所有通过房间密码验证的访客都可以直接操作Pi**，不需要申请或自动取得租约，没有另外分配的“只读访客”类别。公共房间入口为所有访客统一赋予Pi操作权限；只有开启审批且尚未获批、或授权已失效时，访客暂时只能查看。房间密码、当前会话范围和命令校验仍有效；房间设置、修改密码和审批其他人仍由房主本机页面管理。

房主在办公电脑打开本机工作台（通常`http://127.0.0.1:37891`），登录后进入「分享房间 → 房间设置 → 启用控制权审批」，确认后才开启。此开关按房间持久化，旧房间未设置时也默认为关闭。公共网站和远程访客不能修改开关、批准申请或强制接管。审批开关由房主本机页面管理；具体申请也可通过经过本机房主认证的 Pi `/cafe approvals` 命令批准或拒绝。

开启后，访客未获批准便点击发送时，会直接弹出带「申请控制权」按钮的对话框，而不是只在底部显示文字。申请仍须访客明确点击，弹窗只处理申请、不持有待执行的消息。房主本机页面显示待审批数量、申请编号、访客和Pi实例。房主逐项批准或拒绝；不打开页面、关闭页面或超时都不会自动批准。批准前可以查看与写草稿，但任务不发送；批准后仍须访客自己点击发送，不重放之前被拒绝的任务。一个Pi实例同一时刻只授予一个远程连接，已有持有者必须先由房主撤销或自行释放，不能通过批准新请求悄悄替换。

申请90秒未处理会失效。登录时可自定义昵称，统一显示为「昵称#固定ID」。浏览器为每个房间保存不可导出的签名密钥，ID来自公钥摘要；昵称不是权限凭据。同一浏览器刷新或短时断线后，通过密码和新的连接签名验证，可在5分钟重连窗口内恢复原批准，不新建审批。改昵称不改ID，同昵称不同浏览器仍有不同ID。旧版没有签名身份的访客不迁移旧授权，首次升级后需重新登录/申请；不同浏览器、无痕窗口或清除网站数据也会产生新身份。房间密码不保存，整页刷新后仍需重新输入密码。

在线租约仍为30秒，由活跃页面每10秒续期；过期、主动释放、房主撤销、改密码/重置链接、切换审批或重启网关后不能恢复旧批准。正在运行的任务不会被刷新或授权撤销自动取消。存储不可用时明确提示当前身份仅临时有效，不假称刷新可恢复。房主可随时撤销；撤销、切换策略和到期只限制后续操作，不自动取消已经运行的任务。关闭审批后所有有操作权限的访客恢复直接操作，旧申请和授权清空。这个功能不锁住办公电脑的本地终端。

访客不能通过房间修改密码/key，也不能远程任意创建本机进程。独立实例默认关闭。房主明确配置`roomManagement:true`和`--managed-config`后，控制审批关闭时operator可在批准项目中创建/打开独立Pi，但不能关闭他人实例；控制审批开启时，请由房主本机页面创建/打开独立实例，远程访客仅对已有Pi申请操作。普通Pi的“新建会话”仍要求空闲、当前权限及确认；受管Pi固定自己的会话，使用“新实例”。工作目录白名单不是OS沙箱，模型和工具仍按办公端原权限执行。

设置保存为房间身份文件旁的`.control.json`，不改房间链接、密码或私钥。申请与授权只保存在网关内存中，重启后不会继承未完成申请或旧批准。配置损坏时拒绝启动，不悄悄退回关闭状态。旧的非房间远程设备模式保持其原有协调协议。

当前一个网关房间对应 `main`；其他逻辑room需明确配置迁移，不会自动把原本未授权的房间内容加入。原生Pi仍负责模型调用、工具、文件访问策略及JSONL；云端不持有会话执行所有权。

## 独立实例管理的配置位置

目前没有网页配置编辑表单，不能从房间设置里填写项目路径或启动参数。当前安装的房间配置是`~/.config/pi-cafe-space/rooms-space/room-device.json`，其中`roomManagement`缺省为false；开启需要同时指定独立管理配置，并非仅切换审批开关。管理JSON通过`room-run --managed-config /绝对路径/manager.json`加载，名字可自行指定，包含node、cli、extension、agentDir、stateDir、env和projects。完整格式见[MANAGED_SESSIONS.md](MANAGED_SESSIONS.md)，其Windows示例路径必须按实际系统替换。

当前Mac受管启动参数位于`~/Library/LaunchAgents/com.cafecodework.pi-cafe-relay.plist`。未提供--managed-config时没有默认的项目配置文件可找。本轮只说明位置，没有启用独立实例管理、开放任何目录或替用户选择启动配置。独立实例由网关拥有，网关退出会回收其管理的后台进程；手动启动的Pi不在此回收范围。

## 手机界面与工作状态

手机顶部点当前实例名称切换Pi，文件与更多选项分别打开抽屉；语言、主题、连接详情和协作管理不再常驻占据聊天空间。输入框固定在可视区域底部，手机回车换行，发送按钮才提交（硬件键盘Ctrl/Cmd+Enter仍可发送）；键盘高度变化适配基于visualViewport。

消息区的活动条区分真实思考、回复、工具运行及等待本机确认。还没有思考内容时只显示处理中，断线时不继续冒充实时状态；计时从本次观察开始，不代表计费时间或预计完成进度。思考详情折叠可展开。活动标记为固定SVG咖啡杯和轻微蒸汽，不使用会被iPhone替换成彩色emoji的字符；减少动态效果时蒸汽停止。回到最新按钮属于消息区域，不覆盖活动状态与计时。

手机正文的列表项、段落、标题和代码块分别留白，行内代码适度缩小并按行包裹背景；没有改变消息原文。输入框聚焦只强调原圆角表面，不再出现叠加的方框；发送方式在任务运行且开始输入后出现，仍需明确选择才能提交，不自动推断发送语义。

工具以紧凑的名称、目标文件/命令、状态和增删摘要呈现。手机使用可换行的统一diff，长内容可展开；编辑参数生成的内容标为“请求的修改”，只有工具返回结构有效的diff才标为返回变更，均不替代实际文件验证。原始参数与输出保留在展开区。呈现参考同仓库pi-theme-cafecode，不改变工具执行语义。

Pi状态栏即时显示连接状况，但短于10秒的重连不打印告警；一次连续故障最多一次警告，恢复持续稳定60秒才提示一次恢复。实际持续离线仍可通过/cafe status核对。升级扩展后已有Pi需在空闲时/reload，旧屏幕中已经打印的警告不会被自动删除。

## P2P与身份验证

房间key是本机P-256公钥的规范base64url编码，具有稳定身份，不只是一个任意可抢占的短名称。办公端向云端登记时签署一次性挑战，持有分享链接不等于能冒充房主。访客随机数、当前信令会话、offer和answer的SHA-256摘要均纳入办公端ECDSA签名。浏览器以链接里的公钥验证应答，验证通过才接受DTLS握手和发送密码。

密码只通过已验证的可靠有序WebRTC DataChannel发给办公端。密码正确前不创建业务Hub连接，不传送Pi实例、历史或文件。办公端保存独立随机盐与PBKDF2-HMAC-SHA256（600000次）校验值，不保存房间密码明文；文件与目录受操作系统用户权限保护，不是加密保险库。密码计算采用有界并发与房间级资源额度，一次连接只有一次密码尝试；密码错误、验证忙碌、资源限流和房间已变化分别返回对应提示，不把正常并发或成功验证误当作密码失败锁定。具体额度以当前实现为准，变更与验收见[开发交接](DEVELOPMENT_HANDOFF.md)。

直连不可用时可使用配置好的TURN，中继后数据仍由浏览器和办公网关的DTLS端点处理，界面区分直连/TURN。**新房间模式不静默回退到承载业务明文的云端WSS中继。** WebSocket仅交换房间定位和连接信令，不能提交房间业务数据或密码。TURN本身仍需配额、短期凭据、防火墙和运维限流；此前已有TURN部署可复用。

这不等于“无需信任网站”：公共网页的JavaScript代码仍是信任边界，恶意网页更新可读取用户输入。roomKey放在URL fragment使它不进入首次HTTP URL，但后续信令必须使用房间key。浏览器历史/分享记录仍可能保留链接。强度较低的房间密码更容易被猜测，用户可自行选择随机密码。

## 新办公电脑配置

预构建包新增以下命令。先完成普通本机网页初始化，设置本机6–20位令牌；启动房间模式时使用同一凭据文件。避免同时启动两个程序监听相同端口。

```sh
# 在新预构建包目录内执行；输出目录必须不存在。
node scripts/remote/room-setup.mjs \
  --out "$HOME/.config/pi-cafe-space/my-room" \
  --origin https://space.cafecode.work \
  --name "我的办公电脑"

node scripts/remote/room-run.mjs \
  --config "$HOME/.config/pi-cafe-space/my-room/room-device.json" \
  --credentials "$HOME/.config/pi-cafe-space/credentials-37891.json" --check

# 替换旧网关的受控启动方式后启动；--check只校验，不会抢占旧端口。
node scripts/remote/room-run.mjs \
  --config "$HOME/.config/pi-cafe-space/my-room/room-device.json" \
  --credentials "$HOME/.config/pi-cafe-space/credentials-37891.json"
```

房间配置包含 `mode:device`、`publicOrigin`、`cloudUrl:wss://<host>/room/host`、`roomIdentityFile`、`deviceName`、`rooms:[main]`、`maxRole:operator`、`enableWebRTC:true`。无云端用户token，也不需要服务器增加设备记录。身份文件第一次由网关创建，后续密码/key变更私有落盘；不要复制同一个身份文件给两个独立房主。

云端配置开启 `roomAccess:true` 和 `enableWebRTC:true`。旧Users/Devices可备份后移除；保留TURN配置。公共模式关闭旧设备目录和旧远程账号接入路径。`/api/room/share`只存在于办公端，并要求loopback地址、同源、固定Host、JSON、自定义请求头和本机登录令牌。它不返回密码或私钥。

## 复验

- Go：`go test -race -count=1 ./internal/remote -run TestRoom`，含实际Pion直连和强制TURN，验证候选类型确为relay。
- Web：包内Vitest的 `roomCrypto.test.ts`、`RoomSocket.test.ts`，含签名篡改/重放、不在信令发密码以及认证前拒绝业务数据。
- 浏览器：`scripts/remote/room-browser-test.mjs --binary <候选绝对路径> --browser <独立Chrome绝对路径> --report <独立报告目录>`。它在随机本机端口、新临时身份和合成Pi中执行，二维码用独立jsQR真实解码，验证复制URL、错误密码、两个访客、单次任务、密码更新、链接重置、320/390px布局及重启。真实provider请求为0。

本轮已发现并修复Go省略空ICE列表而浏览器误判的问题。隔离浏览器通过不等于蜂窝网络、真机锁屏或任意公司防火墙均通过；线上实际验收与部署路径单独记录在DEPLOYMENT_SPACE.md。参考W3C WebCrypto规范的ECDSA原始签名格式、RFC8827以及qrcode.react官方文档。
