# 房间版架构、能力与安全复核

2026-10-03。范围为当前房间实现、安装引导及已部署拓扑的定向复核；不是全仓逐行审计、密码协议证明或第三方渗透测试。优先保持用户要求的“公共页面＋房间链接/二维码＋密码＋P2P”，不再次引入云端账号体系。

## 总体判断

Pi负责执行、工具和JSONL；办公网关负责本机实例投影、房间身份与访客授权；云端负责公共网页和信令；TURN只提供受限网络中继。主执行边界合理，没必要再替换Go/React或引入数据库/微服务。新增room_identity、room_cloud、room_agent及RoomSocket已把房间身份、信令和业务门禁分开，但其跨语言契约与生命周期仍需要持续回归。

一台办公电脑一个房间，内部多个Pi。房间key固定公钥并用于签名验证，不把链接当成密码。办公端对offer/answer和会话挑战签名后，浏览器才接受该端点并发送密码；密码验证前没有业务Hub连接。因此当前设计没有把“WebRTC连接已建立”误当成“有权读取Pi”。公共网站的JavaScript代码依然是信任边界，不能宣称网页供应链失陷时也绝对看不到密码。

## 能力和权限清单

| 角色/状态 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 公共首页访客 | 输入链接/key或扫码进入房间页 | 枚举所有房间、电脑、会话 |
| 有链接但未通过密码 | 建立有界信令/认证连接 | 获取Pi列表、历史、文件，提交业务命令 |
| 通过密码的访客 | 查看main范围实例和会话，申请实例控制权 | 修改房间密码/key，强制夺取其他访客控制权，使用本机管理员进程管理入口 |
| 持有实例控制权的访客 | 通过原生Pi支持的命令执行任务 | 自动获得操作系统root或绕过Pi自身权限策略 |
| 本机已登录房主 | 查看分享URL/二维码，明确修改密码或重置链接 | 无需确认就改其他站点/账户/模型配置 |

**这不是只读分享。** 链接和密码的持有者可申请控制Pi；Pi工具实际能访问什么，仍由运行Pi的本机账户及工具策略决定。没有多人实名账号时，访客昵称不能用作可靠审计身份。只应分享给信任的人；已经增加分享界面的权限提示与初始密码来源说明。

## 本轮复现并修复

### 1. 无效请求可以耗尽全站房间连接预算

修复前，合法Origin但根本不是WebSocket升级的GET也进入全局120次/分钟计数。新增测试中第121个无效请求返回429，证明它消耗了其他房间共用的预算。

现在先拒绝非WebSocket升级；解析并找到真实在线房间后才消费该房间自己的预算。不同房间预算隔离，未知key不创建额外限流状态；同一在线房主重连沿用已有预算。连接总数、每IP并发、消息上限和密码尝试限流仍保留，不通过取消限流修复。房间预算达到上限时返回明确繁忙状态。

### 2. 已发送密码后的异常仍可能显示“没有发送密码”

修复前，任何信令异常被归为ROOM_IDENTITY_FAILED；即使密码已经通过验证过的DataChannel发送，也可能显示“没有发送密码”。新增前端测试先完成身份验证和密码发送，再注入错误会话信令，实际得到错误分类，修复前失败。

现在区分认证前身份失败和之后的协议错误；只有密码尚未送出的身份验证阶段可以显示该保证。后续连接异常明确中止并提示重连，不自动重放任务，也不降低验签要求。

## 已有保护与具体边界

- 同源/字面Host/loopback门禁保护本机分享接口；JSON严格解析拒绝重复键，长度/深度有上限。密码、房主私钥、PBKDF校验值不返回分享接口。
- 密码校验使用独立盐和PBKDF2-HMAC-SHA256工作因子600000；密码仍由用户选6–20位，不强制字符组合。工作因子只提高猜测成本，不能把弱密码变成强密码。
- 每连接一次密码尝试、每房间每分钟12次昂贵校验；密码更新和链接重置都撤销现有访客。状态以本机文件保存，重启保持，更新有revision和文件摘要检查。
- 密码和业务只走签名绑定端点后的DataChannel。新房间模式不静默转为云端业务WSS；直连/TURN路径如实显示。消息分片、队列、缓冲和超时有上限。
- 部署cloud仅映射宿主机127.0.0.1，TURN使用host网络并显式添加窄端口规则；容器非root、只读根、无额外capabilities。避免以UFW默认规则误以为所有Docker发布端口都受相同保护。
- 原本机登录token文件仍是OS权限保护的明文凭据，房间密码则是加盐校验值。不要把二者混称加密密码保险库。本机管理员/同账户与网站脚本必须受信任。

## 未在本轮悄悄改变的风险与取舍

| 风险/限制 | 影响与建议 |
| --- | --- |
| 共享密码没有个人身份 | 无法永久只撤销某一个知道密码的人；需要改密码。不同权限邀请、逐访客撤销、操作审计属于下一层产品设计，不能仅靠昵称实现 |
| 公共匿名房主登记与TURN配额 | 仍可能被恶意批量注册、握手或资源耗尽影响；现有有界资源并不等于抗大规模DoS。广泛开放前要完善边缘限流、监控与滥用处理策略 |
| 反代后的来源IP | 当前连接限制依赖实际对端地址；经Caddy转发的访问可能共用一个源地址。未擅自信任任意X-Forwarded-For/CF头。扩展公共规模前应明确可信代理链与直连阻断，再实现可靠来源限制 |
| 正确密码并发/限流 | 为限制昂贵校验，同房间同时验证可能提示密码或频率问题；暂未加无限排队。可在后续采用有界认证队列及更细错误语义 |
| 认证前ICE资源 | 已知链接的访客仍可消耗有限ICE/DTLS和TURN资源；实例数据不泄漏不代表没有资源攻击面 |
| 网络和长连接 | Mac原公网UDP测试受隧道路由影响；TURN/TLS5349尚未配置。未做一小时以上凭据到期、换网与手机锁屏连续测试 |
| 程序供应链 | 直接axios已升级到1.20.0，但工作区还有其他开发依赖审计项；未执行全仓强制升级，不声称零漏洞 |
| 文件渲染/全部工具权限 | 本轮不是所有历史渲染器和Pi工具的完整审计；远程取得Pi控制权意味着真实任务权限，不应分享给不可信者 |

## 体验建议

保持入口简单：本机登录→分享房间→复制/扫码→房间密码→Pi。不要恢复旧云端访问密钥、设备目录或main选择步骤。房间密码修改与链接重置分别明确提示撤销范围，连接中/离线/繁忙/验签失败应分开，不用一个“密码错误”覆盖全部情况。

共享密码及房间管理员身份采用当前设计是合理的个人/小团队取舍；不把它包装为企业级多租户权限系统。当前可用版本的验收范围和部署摘要见refactor/ROOM_ACCEPTANCE.md与DEPLOYMENT_SPACE.md。
