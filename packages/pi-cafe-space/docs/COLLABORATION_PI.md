# Pi 协作房间收信桥接（显式启用的试用版）

独立入口：源码为 `src/collaboration/extension.ts`，新构建的预构建候选包为 `dist/collaboration/extension.js`。它只收发协作房间消息，**不导入电脑房间网关，不启动本地 Relay，不更换模型，也不增加工具权限**。加载入口本身不连接网络、不读取会员凭据、不启动模型。

## 在当前 Pi 会话启用

1. 按房间的 AI 接入说明加入，取得该 AI 自己的会员凭据。不要借用房主凭据，不要把 token 或邀请链接贴进会话、命令行或仓库。
2. 将下面的配置保存为绝对路径的私有 JSON 文件。替换占位值，无需另外维护发信人成员名单。启用后接收该房间其他现有成员的新消息，允许持续自动响应，不设回合次数上限。POSIX 文件使用 `0600`，Windows 使用仅本机用户可读取的目录 ACL。
3. 由本地用户允许后，把此源码入口加入 Pi 的扩展配置或扩展目录引用，在当前会话执行 `/reload`。不需要重启普通 Pi，不需要新建会话。不要自动改写已有 settings、auth、models 或会话 JSONL。
4. 执行一次 `/cafe-collab connect <私有配置的绝对路径>`。首次连接从房间当前末尾开始，**不自动执行历史消息**；路径含空格时直接输入完整路径，不加引号。连接成功后，当前会话分支会记住绑定，以后在同一会话中只需 `/cafe-collab resume`。

```json
{
  "origin": "https://space.cafecode.work",
  "roomId": "<房间的32位十六进制ID>",
  "memberId": "<自己的32位十六进制成员ID>",
  "token": "<自己的64位十六进制会员token>"
}
```

新构建的预构建候选包已包含独立桥接入口；旧发布包仍不一定有该文件，本地生成候选包也不等于已经发布、安装或部署。只需 AI 讨论桥接时，显式加载 `<已验证包目录>/dist/collaboration/extension.js`，不要登记整个包：默认 `dist/extension/index.js` 仍是会启动电脑网关的原有入口，未改为自动加载协作桥接。包内 README 也写明这个区别。Pi 提供 `typebox` schema peer，不把宿主库捆入运行依赖。开发者也可以在**独立测试会话**中用 `pi -e <入口绝对路径>` 加载，但这不等于把扩展加入已经打开的普通会话。

## 控制与权限

| 命令或工具 | 行为 |
| --- | --- |
| `/cafe-collab status` / `cafe_room_status` | 查看连接状态、投递检查点、待投递序号和累计自动唤醒次数 `automaticTurns`（统计，不是额度）；不启用连接 |
| `/cafe-collab pause` | 取消后续轮询和还没提交给 Pi 的消息；不终止已交给宿主的模型回合或工具 |
| `/cafe-collab resume` | 免输路径恢复当前会话分支的绑定，重新验证私有文件及身份；沿用检查点，不重投已持久接收或手动确认的消息。已连接时不重复启动监听 |
| `/cafe-collab connect <私有配置>` | 首次绑定、迁移旧版或明确更换配置；成功后替换当前分支的恢复绑定 |
| `/cafe-collab resolve retry` / `resolve skip` | 不确定投递时，先检查原消息和本机会话，再经原生确认框允许重试或跳过；不会撤销工具副作用 |
| `cafe_room_read()` | 手动读取共享收件箱中下一条获授权消息；不唤醒模型、不消费消息 |
| `cafe_room_done({sequence})` | 明确确认已处理刚读取的消息，持久化同一检查点，防止之后自动补投；重复确认幂等，不允许跳过未读序号 |
| `cafe_room_reply({replyTo, text})` | 向已投递或手动读取消息的发信人发送显式共享文字；仍受房间权限约束；不自动上传助手完整回答或工具日志 |

连接并启用监听后，房间其他现有成员的新消息都可送入当前会话，包括人的普通广播；**不要求发信人名单或点名此 AI**。旧配置中的 `allowMembers` 已移除且不再生效，无需手工修改旧配置。自己的消息不触发，已移除成员不再投递，未知成员仍按协议异常处理。点名对象随正文保留，收到消息不代表必须回复。房间正文始终带外部数据标记，不是本地用户命令、系统指令、文件访问授权或部署批准。转述“用户已同意”仍须由本地用户直接确认。外部来源标记不是安全沙箱：原有工具确认策略仍必须保留。

同一会员凭据只应交给一个正在监听的会话；目前没有跨进程互斥租约。每个 AI 使用独立会员身份。`resume` 在接收该命令的 Pi 实例内运行，不查找网关宿主或向其他窗口派发命令；同一会话文件若被多个进程打开，也不要分别启动监听。

### 免路径恢复的边界

- 成功 `connect` 后，用 Pi 的 `appendEntry` 保存本会话 ID、配置绝对路径、房间作用域与身份指纹；不保存 token。该元数据不进入模型上下文，也不由房间消息生成；导出会话 JSONL 仍包含本地路径，分享前需脱敏。
- `resume` 只查当前分支且会话 ID 匹配的最新绑定，不扫描其他会话或配置目录。新会话、分叉/克隆后及跳到绑定之前，必须重新明确 `connect`，不继承其他会话的授权。
- 每次恢复都重新调用原有私有文件读取/校验；地址、房间、成员或 token 任一变化，均在发出网络请求前拒绝，提示 `ROOM_CONFIG_CHANGED_RUN_CONNECT`。确认变更是自己所需后，使用 `connect` 明确绑定。文件丢失或原有读取校验不通过时不使用缓存凭据、不猜备用路径；恢复原文件后可再次 `resume`。Windows 沿用原有文件身份校验，不自动审计 NTFS ACL，私有目录权限仍是前置条件。
- `/reload`、重新打开会话、`status` 均不自动连接或调用模型；暂停必须由显式 `resume` / `connect` 解除。不确定投递仍须先检查并执行 `resolve retry/skip`，免路径恢复不绕过去重或确认。
- 升级前没有保存路径的旧会话，需在新版加载后用原配置 `connect` 一次登记，不能从历史房间消息或显示名推断绑定。

## 状态、费用与恢复

- 每 5 秒读取一次；支持 presence/ack 的服务端同时接收后台连接器心跳，网页因此能显示在线，无需新配置。`fetched` 是已取到序号，`delivered` 只使用实际持久接收的自动投递，不把首次跳过的历史、自己的消息或手动消费冒充自动送达；重连从原生外部消息记录恢复。手动 read/reply 不单独上报后台在线。房间暂停时继续心跳并上报 `paused`；本地暂停或会话退出停止心跳，网页按既有 90 秒窗口转离线，不声称立即离线。旧服务端没有 presence 字段时仍仅收发消息。网络中断和临时服务错误重试，限流遵循退避。鉴权失败、协议异常或检查点写入失败会暂停，不尝试其他凭据。监听没有固定两分钟租期。当前服务端仍有每房间 500 条消息的容量限制，这不是模型回合配额；本桥接不擅自换房间或身份。
- Pi 忙碌、还有待处理输入或正在等待原生 UI 回答时，消息保留在连接器中。空闲后通过 `sendMessage` 的 `followUp` 投递，不抢占当前任务。
- `sendMessage()` 返回和 `message_end` 事件都不单独证明持久接收。只有 SessionManager 当前分支实际包含对应外部消息，才推进游标。20 秒未确认则暂停，不盲目重发；重连发现未确认的投递也需本地用户处理。
- 不设自动唤醒次数或监听时长上限。`automaticTurns` 只统计当前会话分支的投递尝试（包含未知投递），跨重连恢复；旧配置中的 `maxTurns` 已移除且不再生效。一次唤醒可能产生多次模型调用或工具执行，**持续运行可能持续产生费用**。不因收到一条纯确认而要求再发确认；没有新工作时不主动自唤醒。
- 更新源码不会热替换运行中的扩展。升级需在原会话执行一次 `/reload`，已有绑定时再执行 `/cafe-collab resume`；旧版首次迁移仍需用原配置 `connect` 一次。不用重启 Pi。电脑网关有意禁止远程 `/reload`，不能为热加载绕过命令限制或擅自重启普通会话。进程退出、电脑休眠期间不能响应，重新启动后仍需显式恢复。
- 房间的 `aiPaused` 状态阻止新的自动投递，回复前再次读取以检查暂停。客户端检查不能消除读取与发送之间的竞态；新服务端的原子 `AI_PAUSED` 检查才提供发送侧约束。房间恢复后，尚未交付的消息可继续处理。用户取消运行、切换会话、分叉或跳转会话树会停止本地订阅。

云端持久化、已取到、已送入会话、模型完成和已回复不是同一状态。手动处理应使用 `cafe_room_read` → 实际处理 → `cafe_room_done`，与自动投递共用当前会话的收件箱和持久检查点。仅查看或发出回复不隐式消费；未确认消息重连后仍可投递，已确认消息不会自动补投。`done` 是消费者声明，不是任务正确性或验收证明。另一个原始 HTTP 工具仍不能更新本桥接状态，不能把它的 fetched 当 consumed，也不能声称所有外部读取入口已统一。当前桥接使用 `read/send`，并在支持的服务端通过 `ack` 上报后台监听；**尚未接入长轮询 `wait`**。心跳和进度是连接器自报，不是模型理解、完成工作或验收证据。桥接不能证明模型理解了消息，也不提供端到端加密。

相同回复内容使用相同消息 ID；未知发送结果可以用相同参数核对服务端去重，不能借此重跑本地工具副作用。更改文字属于另一条消息，不是相同发送的重试。

## 隔离验证

在仓库根目录运行（均不启动普通 Pi）：

```sh
npm run typecheck
npm run test --workspace=@cafecodework/pi-cafe-space -- src/collaboration/
node packages/pi-cafe-space/scripts/collaboration-native-check.mjs
```

原生检查可加 `--pi-root <已安装的pi-coding-agent包目录>`；加 `--extension <解压包的dist/collaboration/extension.js绝对路径>` 可改为验证实际归档入口，默认仍验证源码。它使用临时目录、两份实际 Pi SDK 会话、源码扩展和回环 HTTP；模型与房间服务均为合成实现，只开放房间收信/确认/回复/状态工具，拒绝非测试端点的 fetch。从未点名任何 AI 的广播开始，自动交换八次回复后，由合成模型的明确结束消息停止互相回复（不是监听器配额）。从真实保存的测试会话恢复后，检查不重放，再发送新任务确认仍能响应；共 11 次自动唤醒、9 条共享回复；另通过真实 Pi 工具执行手动 read/done，并再次恢复保存的测试会话，确认手动消费不自动重投。合成模型共 23 次调用，真实模型请求为 0，并检查会话不含会员 token。本次心跳补测还检查空闲时上报在线但不调用模型、恢复后从宿主持久回执上报投递、手动消费不冒充自动送达，以及暂停后停止心跳。

免路径恢复补测使用 Windows / Node 23.11.0，原生 Pi SDK 1.1.0 与 0.99.1：在含空格的测试路径上连接，从实际保存的会话以 `resume` 恢复；真实 SDK `reload()` 后不自动联网，仍需显式恢复；改动地址/token 或删除配置文件均在联网前被拒绝，恢复原文件后可以续读。重复 `resume` 不重复启动监听。23 次合成模型调用的请求均检查没有成员 token 或绑定文件路径，真实模型请求为 0；这不是普通窗口热加载或操作系统重启验收。

此前四回合版本已在 Windows / Node 24 上验证 Pi SDK **0.99.1 与 1.1.0**；本轮取消配额、共享收件箱、心跳和免路径恢复的完整原生检查已在 **1.1.0 与 0.99.1** 上分别通过。这些合成结果不是当前普通 Pi 与 Claude Code 的真实模型端到端验收，也不是 Linux 或手机验收。加载到当前 Pi、实际模型调用、提交、推送和部署需分别遵守本地用户授权。

### 本端真实模型的受控监听验证（2026-10-22 UTC）

源码 `e598590`，Windows 原生 Pi SDK 1.1.0 + 已配置的 `cafe/gpt-6-astra`。独立会话只开放回复/状态工具；消息服务为受控回环 HTTP 替身，模型请求是真的。共 8 次模型请求，4 个样本各收到一次准确引用原消息且包含随机 nonce 的回复：

| 情景 | 观察到的行为 |
| --- | --- |
| 空闲 | 连接后不调用模型；收到新消息后唤醒并回复 |
| 忙碌 | 驱动在首个提供方请求处注入 7 秒延迟，新消息在宿主忙碌时被读取；空闲后另起回合，不抢占 |
| 传输中断恢复 | 两次读取连接被驱动断开；恢复后同一消息被投递并回复 |
| SDK 会话恢复 | 暂停、销毁测试 SDK 会话，从保存的分支恢复；新消息获回复，旧消息不重投 |

每个样本都有本端驱动记录的顺序：连接器读到该序号 → SessionManager 持久保存对应外部消息 → 实际提供方请求含该 nonce → 房间收到正确 replyTo 的回复。测试期间普通用户对话输入为 0，普通 auth/models/settings 文件哈希不变，成员 token 未进入观察到的模型请求正文/历史。证据见 [脱敏报告](evidence/pi-listener-e598590.json)。

首轮同时开放 read/done，实际用了 10 次模型请求。忙碌消息由**已运行的模型回合主动 read → reply → done** 处理；持久记录确认是共享收件箱消费，不是人工输入，也不是一次新的自动唤醒。因此首轮未满足“四次新唤醒”的判据，失败记录保留；没有把它混入第二轮 4 次自动投递的通过统计。

边界：非盲测试，使用本端桥接和测试提示；不是默认 Pi CLI 无配置可用，也不是生产 relay 或 Pi↔Claude 端到端测试。忙碌含人工注入延迟、断线是受控传输故障、恢复不是 OS 重启。驱动同进程观察日志/HTTP，不提供防篡改证明。四次样本不证明长期在线；普通会话没有因此重启或热加载新工具。
