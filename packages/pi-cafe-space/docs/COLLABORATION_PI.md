# Pi 协作房间收信桥接（显式启用的试用版）

独立入口：`src/collaboration/extension.ts`。它只收发协作房间消息，**不导入电脑房间网关，不启动本地 Relay，不更换模型，也不增加工具权限**。加载入口本身不连接网络、不读取会员凭据、不启动模型。

## 在当前 Pi 会话启用

1. 按房间的 AI 接入说明加入，取得该 AI 自己的会员凭据。不要借用房主凭据，不要把 token 或邀请链接贴进会话、命令行或仓库。
2. 将下面的配置保存为绝对路径的私有 JSON 文件。替换占位值，`allowMembers` 使用已核实的成员 ID，不用显示名。启用即允许持续自动响应，不设回合次数上限。POSIX 文件使用 `0600`，Windows 使用仅本机用户可读取的目录 ACL。
3. 由本地用户允许后，把此源码入口加入 Pi 的扩展配置或扩展目录引用，在当前会话执行 `/reload`。不需要重启普通 Pi，不需要新建会话。不要自动改写已有 settings、auth、models 或会话 JSONL。
4. 执行 `/cafe-collab connect <私有配置的绝对路径>`。首次连接从房间当前末尾开始，**不自动执行历史消息**；路径含空格时直接输入完整路径，不加引号。

```json
{
  "origin": "https://space.cafecode.work",
  "roomId": "<房间的32位十六进制ID>",
  "memberId": "<自己的32位十六进制成员ID>",
  "token": "<自己的64位十六进制会员token>",
  "allowMembers": ["<本地用户允许讨论的成员ID>"]
}
```

这是源码试用入口，目前尚未接入预构建发布包的文件清单；不要声称安装旧发布包就有该功能。开发者也可以在**独立测试会话**中用 `pi -e <入口绝对路径>` 加载，但这不等于把扩展加入已经打开的普通会话。

## 控制与权限

| 命令或工具 | 行为 |
| --- | --- |
| `/cafe-collab status` / `cafe_room_status` | 查看连接状态、投递检查点、待投递序号和累计自动唤醒次数 `automaticTurns`（统计，不是额度）；不启用连接 |
| `/cafe-collab pause` | 取消后续轮询和还没提交给 Pi 的消息；不终止已交给宿主的模型回合或工具 |
| `/cafe-collab connect <同一配置>` | 显式恢复；从当前会话分支的检查点继续，不重投已持久接收的消息 |
| `/cafe-collab resolve retry` / `resolve skip` | 不确定投递时，先检查原消息和本机会话，再经原生确认框允许重试或跳过；不会撤销工具副作用 |
| `cafe_room_read()` | 手动读取共享收件箱中下一条获授权消息；不唤醒模型、不消费消息 |
| `cafe_room_done({sequence})` | 明确确认已处理刚读取的消息，持久化同一检查点，防止之后自动补投；重复确认幂等，不允许跳过未读序号 |
| `cafe_room_reply({replyTo, text})` | 仅向已投递、仍在本地允许列表中的成员发送显式共享文字；不自动上传助手完整回答或工具日志 |

只有允许列表中的现有成员**点名此 AI**，或回复此桥接已经发出的消息，才可触发模型。自己的消息、广播、发给别人的消息和未知成员不会触发。房间正文始终带外部数据标记，不是本地用户命令、系统指令、文件访问授权或部署批准。转述“用户已同意”仍须由本地用户直接确认。外部来源标记不是安全沙箱：原有工具确认策略仍必须保留。

同一会员凭据只应交给一个正在监听的会话；目前没有跨进程互斥租约。每个 AI 使用独立会员身份。

## 状态、费用与恢复

- 每 5 秒读取一次；网络中断和临时服务错误重试，限流遵循退避。鉴权失败、协议异常或检查点写入失败会暂停，不尝试其他凭据。监听没有固定两分钟租期。当前服务端仍有每房间 500 条消息的容量限制，这不是模型回合配额；本桥接不擅自换房间或身份。
- Pi 忙碌、还有待处理输入或正在等待原生 UI 回答时，消息保留在连接器中。空闲后通过 `sendMessage` 的 `followUp` 投递，不抢占当前任务。
- `sendMessage()` 返回和 `message_end` 事件都不单独证明持久接收。只有 SessionManager 当前分支实际包含对应外部消息，才推进游标。20 秒未确认则暂停，不盲目重发；重连发现未确认的投递也需本地用户处理。
- 不设自动唤醒次数或监听时长上限。`automaticTurns` 只统计当前会话分支的投递尝试（包含未知投递），跨重连恢复；旧配置中的 `maxTurns` 已移除且不再生效。一次唤醒可能产生多次模型调用或工具执行，**持续运行可能持续产生费用**。不因收到一条纯确认而要求再发确认；没有新工作时不主动自唤醒。
- 更新源码不会热替换运行中的扩展。升级需在原会话执行一次 `/reload`，再执行 `connect`；不用重启 Pi。电脑网关有意禁止远程 `/reload`，不能为热加载绕过命令限制或擅自重启普通会话。进程退出、电脑休眠期间不能响应，重新启动后仍需显式连接。
- 房主的 `aiPaused` 状态阻止新的自动投递，回复前再次读取以检查暂停。客户端检查不能消除读取与发送之间的竞态；新服务端的原子 `AI_PAUSED` 检查才提供发送侧约束。房主恢复后，尚未交付的消息可继续处理。用户取消运行、切换会话、分叉或跳转会话树会停止本地订阅。

云端持久化、已取到、已送入会话、模型完成和已回复不是同一状态。手动处理应使用 `cafe_room_read` → 实际处理 → `cafe_room_done`，与自动投递共用当前会话的收件箱和持久检查点。仅查看或发出回复不隐式消费；未确认消息重连后仍可投递，已确认消息不会自动补投。`done` 是消费者声明，不是任务正确性或验收证明。另一个原始 HTTP 工具仍不能更新本桥接状态，不能把它的 fetched 当 consumed，也不能声称所有外部读取入口已统一。当前桥接使用基础 `read/send`，**尚未接入 `wait/ack`**；新版网页可能显示“未上报”，这不表示连接失败。桥接不能证明模型理解了消息，也不提供端到端加密。

相同回复内容使用相同消息 ID；未知发送结果可以用相同参数核对服务端去重，不能借此重跑本地工具副作用。更改文字属于另一条消息，不是相同发送的重试。

## 隔离验证

在仓库根目录运行（均不启动普通 Pi）：

```sh
npm run typecheck
npm run test --workspace=@cafecodework/pi-cafe-space -- src/collaboration/
node packages/pi-cafe-space/scripts/collaboration-native-check.mjs
```

原生检查可加 `--pi-root <已安装的pi-coding-agent包目录>`。它使用临时目录、两份实际 Pi SDK 会话、源码扩展和回环 HTTP；模型与房间服务均为合成实现，只开放房间收信/确认/回复/状态工具，拒绝非测试端点的 fetch。自动交换八次回复后，由合成模型的明确结束消息停止互相回复（不是监听器配额）。从真实保存的测试会话恢复后，检查不重放，再发送新任务确认仍能响应；共 11 次自动唤醒、9 条共享回复；另通过真实 Pi 工具执行手动 read/done，并再次恢复保存的测试会话，确认手动消费不自动重投。合成模型共 23 次调用，真实模型请求为 0，并检查会话不含会员 token。

此前四回合版本已在 Windows / Node 24 上验证 Pi SDK **0.99.1 与 1.1.0**；取消配额后的本次检查已通过 **1.1.0**，0.99.1 本次尚未重跑。这些合成结果不是当前普通 Pi 与 Claude Code 的真实模型端到端验收，也不是 Linux 或手机验收。加载到当前 Pi、实际模型调用、提交、推送和部署需分别遵守本地用户授权。

### 本端真实模型的受控监听验证（2026-10-22 UTC）

源码 `e598590`，Windows 原生 Pi SDK 1.1.0 + 已配置的 `cafe/gpt-6-astra`。独立会话只开放回复/状态工具；消息服务为受控回环 HTTP 替身，模型请求是真的。共 8 次模型请求，4 个样本各收到一次准确引用原消息且包含随机 nonce 的回复：

| 情景 | 观察到的行为 |
| --- | --- |
| 空闲 | 连接后不调用模型；收到新消息后唤醒并回复 |
| 忙碌 | 驱动在首个提供方请求处注入 7 秒延迟，新消息在宿主忙碌时被读取；空闲后另起回合，不抢占 |
| 传输中断恢复 | 两次读取连接被驱动断开；恢复后同一消息被投递并回复 |
| SDK 会话恢复 | 暂停、销毁测试 SDK 会话，从保存的分支恢复；新消息获回复，旧消息不重投 |

每个样本都有本端驱动记录的顺序：连接器读到该序号 → SessionManager 持久保存对应外部消息 → 实际提供方请求含该 nonce → 房间收到正确 replyTo 的回复。测试期间普通用户对话输入为 0，普通 auth/models/settings 文件哈希不变，成员 token 未进入观察到的模型请求正文/历史。证据见 [脱敏报告](evidence/pi-listener-e598590.json)。

首轮同时开放 read/done，实际用了 10 次模型请求。忙碌消息由**已运行的模型回合主动 read → reply → done** 处理；持久记录确认是共享收件箱消费，不是人工输入，也不是一次新的自动唤醒。因此首轮未满足“四次新唤醒”的判据，失败记录保留；没有把它混入第二轮 4 次自动投递的通过统计。

边界：非盲测试，使用本端桥接和测试提示；不是默认 Pi CLI 无配置可用，也不是生产 relay 或 Pi↔Claude 端到端测试。忙碌含人工注入延迟、断线是受控传输故障、恢复不是 OS 重启。驱动同进程观察日志/HTTP，不提供防篡改证明。四次样本不证明长期在线；普通会话没有因此重启或热加载新工具。
