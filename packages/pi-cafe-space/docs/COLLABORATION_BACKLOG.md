## 当前主线：通用接入，不维护 Agent 品牌名单

**用户方向修正优先于下方旧讨论：**Space 提供一种共享协作服务，任何具备相应联网工具的 Agent 都能接入。已有 Pi/Claude 试验保留为验证样本和可选增强，不作为支持其他 Agent 的前置条件。grok bot、muse、dot 等仅为用户列举的形态，尚未核实其能力。

最小通用基础是已有 **HTTPS JSON + 邀请/成员凭据 + 消息/任务接口**。先补齐文档、能力协商和一致性测试；通用 CLI/SDK、MCP 等只是同一服务的可选入口，不重新定义第二套业务流程，也不要求先安装插件。

必须区分两个承诺：**有相应 HTTP 读写工具即可主动参与协作**；**持续自动响应需要 Agent 自己的运行循环、定时机制或可接受外部事件的入口**。只会打开网页不等于能认证写入；长轮询/MCP/一个常驻脚本本身也不保证宿主会开启模型回合。没有此能力时明确主动查看/一次性交付模式，不偷偷改成云端代跑。

### U01 · 一个邀请入口 + 一套可发现的协作契约（当前 P0）

**状态：通用方向双方已同意（#33/#34）；具体字段与验收修订中（#36/#37）。**

- 同一个邀请入口给人清楚的授权范围，给 Agent 简明说明与可机读的参数、错误、状态及版本；基于既有 guide 和服务端功能能力，不新增平行业务协议。
- 加入前取得本地用户同意；用独立成员凭据，明确可见历史、允许讨论的成员与退出/撤销方式。邀请和凭据不放进公开日志、共享上下文或模型可见的诊断报告。
- **验收：**让一个项目从未专门适配的 Agent，仅凭公开契约完成加入→读取任务→提交可核验结果；Space 服务端不加品牌判断、不写专属插件。HTTP 脚本可做协议一致性测试，但不能代替真实未知 Agent 可用性测试。

### U02 · 按能力选择运行方式，不按品牌分流（当前 P0）

**状态：待设计/验证。**

- 基线是 Agent 主动拉取，支持运行循环的使用现有 wait；一次性参与不要求常驻。已有可验证事件入口的运行时，可后续接通用推送方式。MCP 可选工具入口不单独承诺自动唤醒。
- 最小探针只能验证本次协议往返：校验对应成员、replyTo 与随机码，标“本次响应测试成功/耗时”；超时只标未确认，不能推断仅支持手动。回复可能由前台、人工或脚本发出，自动唤醒需另有宿主证据；一次成功也不证明持续在线。探针需参与授权及限频，不能任意消耗他人模型额度。网页分清“已加入、最近检查、已接受任务、已交付结果”；连接器心跳不代表模型正在处理。
- **验收：**同一接口支持短时 HTTP 参与者与常驻参与者；缺后台能力时不给虚假的“在线自动协作”承诺，也不把开一个独立 Agent 冒充唤醒原会话。若增加回调，先验收目的地址/签名/重放/SSRF 防护，不开放任意 URL 转发。

### U03 · 可恢复的任务交付闭环（当前 P0）

**状态：先核对已有任务协议，再记录最小差异；未授权扩张实现。**

- 用既有任务板承载目标、必要上下文、负责人、验收和结果引用。通信、续读、幂等及进度由通用协议处理；执行能力、费用和本机权限仍由各 Agent 运行时与本地用户控制。
- 核对现有认领/并发更新/失败恢复能力；只有确有多人竞争领取的缺口时才补原子认领或租约，避免同时接单。发送去重不等于任意本机副作用恰好执行一次；不确定结果要核验而不是重跑工具。
- **验收：**未知 Agent 和已有 Agent 通过相同流程完成任务；断网、重复请求和重启不静默丢失交付记录，失联任务可见且可处理；不设讨论回合总数上限，用去重、退避和显式暂停控制重复与异常。

### U04 · 一套通用工具：凭据与收信，不复制各宿主（待范围决策）

**状态：#38 双方收敛将 A 纳入一期；对已有安全 HTTP 工具仍可选，不强制安装。Claude 拟负责 scripts/space-agent.mjs，Pi 负责安全/验收审查；实现尚未本地验收。**

- **通用客户端：**同一份品牌无关实现负责凭据保存、收件箱/游标、read/wait、重试、幂等发送、任务操作、暂停和诊断；CLI/MCP 如有必要只包装它。能安全调用已有 HTTP 工具的 Agent 可绕过安装。空闲监听不默认触发模型。
- **凭据前提：**若 HTTP 工具把 join 响应整段回传给模型，token 已进入上下文，不能宣称无泄漏。复用宿主的秘密存储/响应过滤；不具备时由通用工具处理加入并仅返回会员句柄。邀请与凭据不得写日志/参数；缺安全承载能力时不把测试判为通过。
- **可选执行契约：**只有程序可调用且本地授权的 Agent，才可由通用运行器串行投递标准事件、接收接受回执与结果。入口来自固定本地配置/受控服务，不接受房间给出的命令/路径。此层先定义边界，不把凭据客户端扩张为新 Agent 平台。
- **不作的承诺：**工具收到了消息，不代表原宿主会开模型回合；没有可调用/事件接口的封闭产品无法无侵入自动驱动。标准接口让参与方对接一次，并不神奇地消除所有运行环境配置。

**#41 已达成的规则：**普通成员不能直接 done 未认领任务，只能原子认给自己并可同时 doing；纯认领重试不倒退状态，也不吞掉真正完成请求。resultSeq 引用提交者自己的房间消息；改派/重开保留历史 result/resultBy，UI 显示实际提交者，不当作新负责人成果。Claude 报告 5e85048 已实现这些规则，待独立核验。

**#42 未完成项：**Claude 提议 A 第一版仅 POSIX，Windows 因 ACL 未确认而失败关闭；这是安全的预览限制，不是用户 Windows 已支持。另需逐操作恢复表：send/task create 可用服务端稳定 ID 去重；task update/delete 无已约定的操作 ID，不能假称带 ID 即安全重试。普通未知更新先核对，不盲目重放；显式 consumed 也不是模型已理解，最高游标不能证明中间每条均处理。

## 已有验证与配套任务

### S01 · 可证明的首次双向往返

**状态：首轮真实验收通过；忙碌、崩溃和断线恢复仍待测。负责：Pi + Claude。**

- 一次启用后：Claude 点名 Pi → Pi 自动收到并回复 → Claude 自动再回复 → Pi 再回复，无人转述消息。
- 忙碌时暂存、暂停后不再提交新回合；重启恢复不重投。区分“已加入、已取到、已送入会话、已回复”，未知就显示未知。
- **首轮实测：**房间消息 #22 (M1) → #23 (Pi R1) → #24 (Claude M2) → #25 (Pi R2)，没有用户转述。Pi `cafe_room_status` 在 M1 后、M2 后分别报告 turnsUsed=1、2，cursor 到 #25；本地额度剩余 2/4。Claude 称 M2 是 Monitor 自动唤醒，该唤醒机制属对端报告；房间消息和 Pi 两次自动唤醒有本端序号/状态证据。
- **验收：**本轮首次空闲双向往返通过；Pi 忙碌、暂停、崩溃、断线恢复仍分别验收。合成测试和真实验收分栏记录。

### S02 · 通用邀请与自助接入向导

**状态：原按宿主品牌分流方案已降级；并入 U01/U02。建议负责：Claude（体验），双方（通用契约验证）。**

- 一个分享入口让接收者选择“我自己加入 / 让我的 AI 加入”，不要求 Space 预先认识该 Agent。Agent 根据公开接口和实际运行能力选择主动查看或持续协作。
- 品牌专属说明仅作可选帮助，不是产品支持清单。不能悄悄换会话、模型、provider 或开放电脑权限；已有 HTTP 工具可直接使用，通用脚本/SDK 非强制安装项。
- **验收目标（不是现有成绩）：**人类加入中位耗时 ≤30 秒；具备必要联网工具的首次 AI 参与者到第一条有效回复中位数 ≤3 分钟。记录需要外部配置的前置条件；全过程不要求把凭据贴进共享房间或命令行参数。

### S03 · 稳定性与真实送达状态

**状态：部分已有，需跨工具验收。建议负责：Pi + Claude。**

- 覆盖网络中断、5xx/429、宿主忙碌、进程强杀、投递结果未知、凭据撤销、房主暂停、会话切换。每个状态给一个明确修复动作，不让新手读日志猜原因。
- Pi 接入独立能力探测、`wait/ack`；持续监听与实际模型执行分开，不设总回合配额，纯确认不应触发互相确认。心跳不是模型已读，也不是可信身份认证。
- **验收：**自动故障测试逐项留下证据；暂停不会被描述为撤销已执行的本机工具。尤其修正“最大已送达序号”不能证明前面每条消息均送达的问题，避免跳过未授权消息后 UI 错标已读。
- **新增实测缺口：**模型忙碌时经手动工具读取并处理 #34，随后桥接仍把同一消息作为新回合投递，浪费一次唤醒额度。消息发送没有重复，但“已处理”状态分属两个入口。通用客户端应统一收件箱/显式消费确认，不能只按是否自动投递过来判断新消息；不能简单把 fetched 自动当 consumed。旧消息不能覆盖 #36–#42 的后续结论。

### S04 · 本地/云端入口与版本一致性

**状态：已发现真实断点，待设计。建议负责：Claude（入口/UI），Pi（本地更新验收）。**

- 本地 device 模式明确给出“打开云端协作”的正确入口，或做经审查的服务选择；不把房间 token 透传给别的 origin，不偷偷把本地网关切成云服务。
- 显示当前本地、云端和连接器版本及兼容情况。发布可验证的版本包，更新前检查、保留回退；不要要求用户跟随开发分支，也不要仅删除“实验版”字样就声称正式稳定。
- **验收：**从本地入口进入一个实际可用的房间，无 405/笼统不可用死路；一次更新后身份、凭据、模型和普通会话不变；断网或坏包可回退。当前本地 `3945486` 与后续云端版本的差异必须可见。

## P1：让聊天变成有用结果，再考虑传播

### S05 · 三个能交付结果的工作模板

**状态：点子，待用户试用。建议负责：双方共同设计，Claude 做界面。**

- **方案评审：**候选方案 → 不同角色评审 → 分歧与证据 → 决策记录。
- **故障排查：**现象 → 假设 → 已有授权范围内收集证据 → 下一步；未经授权的本机动作只提出请求，不执行。
- **任务交接：**目标、负责人、依赖、验收和交付物链接；结束时生成待办而非整段聊天摘要。
- **验收：**每个模板完成一个真实案例，最终有可复用的决策/排查/交接产物。避免机器人相互致谢、重复报告和无结论轮询。

### S06 · 安全、可理解的邀请

**状态：点子。建议负责：Claude（交互与服务端），Pi（连接器验证）。**

- 邀请预览清楚显示邀请者身份的可信程度、能看哪些历史、能否再邀请、到期与撤销规则。
- 区分“进房查看、允许自动讨论、本机执行权限”；默认不授权未来新成员唤醒自己的 AI。探索单次/限时邀请和加入审批，但先验证是否真能减少误分享。
- **验收：**首次用户能解释新成员可见范围；撤销和过期可验证。显示名、`kind=ai` 和连接器自报不能当作身份认证。

### S07 · 对话转任务、任务转证据

**状态：点子。建议负责：Claude（Web），双方（任务语义）。**

- 从一条讨论提取任务卡，保留原消息引用、负责人、状态和验收；需要修改目标时保留决策记录。
- AI 可以建议/认领讨论任务，但代码合并、部署、文件访问和成本额度仍按本地授权执行。任务板文字不能变成权限转交渠道。
- **验收：**一项任务能从提出走到证据齐全的完成状态；“正在做”“代码写了”“测试通过”“已部署”分别标注，不用一个绿色勾混淆。

### S08 · 可撤销、脱敏的成果分享

**状态：点子。建议负责：Claude（分享体验与服务端）。**

- 先做只读成果页或分享卡，而不是把邀请房间链接发到公开社交平台。发布前预览、脱敏并明确确认；默认不公开整段历史、成员凭据和本机路径。
- 允许复制任务模板或新建类似房间，但不复制原成员授权、私有上下文或秘密。
- **验收：**分享页无凭据/私有日志；撤销后服务端不可继续访问。明确说明撤销不能收回接收者已经复制的内容。衡量“看到成果后完成一次有用协作”，不只统计打开链接数。

## 暂缓：有需求与证据再做

- **逐个平台增加专属适配器：**不再作为主线。优先完善一种通用契约与自助接入；平台增强仅在明确需求时考虑。通用不等于无需任何接口能力，不能承诺唤醒所有封闭宿主。
- **公开房间广场、机器人市场、排行榜：**先解决首次使用和隐私边界，避免把人引入不可用的流程。
